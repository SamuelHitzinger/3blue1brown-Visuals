# Existing solutions for explanatory visuals within ten seconds

Research date: **2026-10-16**. Primary-source desk research only; no provider calls, installs, weight downloads, or user-media uploads. Repository context was limited to `package.json` and [the workshop checkpoint](realtime-workshop-checkpoint.md). Provider documentation and repository default branches are mutable; dates below distinguish dated papers from documentation inspected today.

**Recommendation:** keep the warm native renderer and persistent world. First test a compact, source-grounded scene transaction with host-owned geometry/layout/animation, then test a faster inference endpoint on the identical contract. Neither switching rendering engines nor generating complete shaders/SVGs has evidence of solving this application's dominant model-latency and explanation-quality problems. No surveyed system establishes arbitrary-subject, scientifically correct, persistent animation from fresh lecture evidence within ten seconds.

## What the deadline means

The checkpoint already measures roughly 12 ms warm compilation, sub-0.2 ms property updates, and some simple browser submissions under four seconds. Its matched lecture example spends 13.6–13.8 seconds in two serial model stages before presentation; blind visual ratings remain below acceptance. Consequently the meaningful metric is **source evidence available → first scientifically useful visual presented**, plus **time until the complete causal explanation is available**. A title, empty axes, speculative picture, first token, or renderer submission alone is insufficient.

Record ingestion/ASR stabilization, queueing, image upload/prefill, first token, first complete transaction, validation, GPU preparation, first browser frame and final explanation separately. Vendor tokens/second divide only a portion of that path. Treat rejected scenes and deadline misses as failures, rather than calculating latency on successful outputs alone.

## Five architecture bets, ranked

### 1. Compact retained scene transactions with progressive commitment

**Reuse:** the existing persistent world, attachment bindings, rollback and evidence cancellation. Borrow the protocol pattern from [A2UI](https://github.com/a2ui-project/a2ui/blob/main/specification/v1_0/docs/a2ui_protocol.md): independently parseable messages, stable component IDs, separate structure/data updates and progressive rendering. Its v1.0 candidate was updated 2026-06-08; [the project is Apache-2.0](https://github.com/a2ui-project/a2ui/blob/main/docs/public/index.md). It is an available protocol, not evidence of educational quality or latency here.

**Proposed adaptation:** emit a compact causal assertion, evidence references, generic geometry and one complete visual change in a single request. Use parametric curves, meshes, fields, vectors, groups, constraints and parameter bindings; retain procedural escape hatches. Avoid a catalog of subject-specific finished scenes. The host supplies default styling, label attachment, transition interpolation and scheduling. This moves recurring implementation work out of model output without limiting the subject vocabulary.

Each committed chunk must contain a self-contained explanatory step, declared dependencies and a source revision. Validate complete chunk syntax, resource bounds, object references and available invariants before atomic commit. Later text must not silently redefine an already committed assertion. Compile complete chunks in isolation while remaining tokens arrive; never execute incomplete JavaScript. Keep semantic speculation invisible until grounded. Streaming helps only when a useful step finishes materially earlier than the whole response.

**Smallest decisive experiment:** on 12 public, held-out prompts spanning mechanics, geometry, circuits, probability and one unfamiliar subject, compare today's whole-program output with compact transactions at the same model/settings. Require novel geometry and one correction to a running scene. Count tokens and first-useful-frame/final-explanation latency; blind-review motion and causal correctness. This is a screening experiment, not a reliable p95 estimate. Stop if brevity removes explanatory steps or increases wrong commitments.

### 2. Swap inference hardware/provider while holding the visual contract fixed

**Evidence, not measured here:** current [Cerebras catalog](https://inference-docs.cerebras.ai/models/overview) advertises approximately 3,000 tokens/s for `gpt-oss-120b` and 1,850 for `qwen-3.8-27b`, with shared free-trial/pay-as-you-go availability. [Structured output](https://inference-docs.cerebras.ai/capabilities/structured-outputs) and [streaming](https://inference-docs.cerebras.ai/capabilities/streaming) are documented; their combined behavior on the proposed schema still requires a capability probe. [Image inputs](https://inference-docs.cerebras.ai/capabilities/image-inputs) are public preview on shared Qwen 3.8 27B, enabling a possible single multimodal request; the docs flag limitations for precise spatial localization and chart distinctions. Do not assume GPT-OSS has that vision capability.

[Groq's catalog](https://console.groq.com/docs/models) lists approximately 500 tokens/s for GPT-OSS-120B. Crucially, [its structured-output documentation](https://console.groq.com/docs/structured-outputs) currently says streaming and tool use are unsupported with Structured Outputs. Test a bounded whole response there; do not design around an unsupported strict-streaming combination. All rates are provider claims, not readiness benchmarks or quality comparisons with the current Sol model.

**Smallest decisive experiment:** after an endpoint is separately configured, run the same public evidence/prompt/schema through current provider and one high-speed endpoint, with no retries or silent repair. Include a source-image case so perception cannot be hidden outside the timer. Capture actual model, tier, reasoning usage, cold/warm behavior and all failures. Promote only if the quality-qualified deadline success rate improves. These are separate API services; an existing Codex subscription does not establish access or entitlement. No account or payment change was performed.

### 3. Generic relational layout and bounded geometric validation

[Penrose](https://penrose.cs.cmu.edu/siggraph20) (SIGGRAPH 2020; [MIT implementation](https://github.com/penrose/penrose)) separates semantic relationships from rendering styles and solves geometric constraints. [Bluefish](https://vis.csail.mit.edu/pubs/bluefish.pdf) (2024; [MIT implementation](https://github.com/bluefishjs/bluefish)) composes diagrams using declarative relations. These are working graphics systems, not LLM-generation benchmarks.

**Reuse:** relational ideas for label ownership, alignment, containment, spacing and connecting named anchors. Generate constraints or relationships instead of many fragile absolute coordinates. Port a small deterministic subset into animlib or compare adapters offline; do not replace the renderer first. Penrose's reusable domain/style vocabulary is powerful, but requiring a new authored domain for every subject conflicts with arbitrary lecture content. Global optimization also needs an explicit time bound and a fallback to the previous valid layout.

**Smallest decisive experiment:** replay 20 existing or synthetic pathological scenes with detached labels, dense geometry, changing bounds and moving connectors. Compare host relations against hand-generated positions at keyframes *and during interpolation*. Measure overlap, attachment errors, layout runtime and reviewer preference. Layout constraints cannot establish that a force direction or scientific inference is correct.

### 4. Distill a small scene author; use guided decoding for syntax

The directly relevant [September 2026 declarative-UI study](https://arxiv.org/html/2609.04184v1) trains on about 1,015 examples. Its 4B student reports about 98% of teacher semantic score and 97% of visual score, with approximately 8.1 s latency for a workload averaging 1,200 output tokens; the 0.8B point is about 3.4 s on H100. These are two application UI domains, not STEM animation. Absolute 4B visual score is 3.09/5, human calibration is limited, and generalization covers catalog changes rather than arbitrary scientific subjects. Useful recipe: teacher-generated targets, catalog perturbations and explicit binding validation. Not evidence that a tiny model already matches expert explanation.

[XGrammar](https://github.com/mlc-ai/xgrammar) (Apache-2.0; [MLSys 2025 paper](https://arxiv.org/abs/2411.15100)) provides efficient structured decoding. [SGLang](https://github.com/sgl-project/sglang) (Apache-2.0) exposes local serving and speculative-decoding infrastructure. [WebLLM](https://github.com/mlc-ai/web-llm) (Apache-2.0) offers browser/WebGPU inference and structured JSON. These provide mechanisms, not a scientifically competent scene model. Grammar masks cannot repair false physics. Browser inference also competes with rendering for the same GPU; measure contention and initial model loading separately. Model-weight and training-data licenses remain separate from runtime licenses.

**Smallest decisive experiment:** first curate a rights-cleared dataset of source → causal assertion → generic scene delta, with counterexamples, corrections and novel compositions. Compare base versus adapter-trained 3–4B models on held-out *subjects*, without serving a large teacher on the critical path. Before training, measure a warm local model's basic decoding envelope on available hardware; abandon local deployment if it cannot meet the token budget. This is medium-term work, not an immediate dependency install.

### 5. Generated mathematical expressions inside fixed GPU kernels

Shaders are compelling for fields, contours, interference, particles and implicit surfaces: short mathematics can describe many pixels. Prefer a bounded expression AST lowered into known WGSL kernels, with host-owned camera, labels, IDs and transitions. Compare against the existing procedural geometry path before adding it. This is an expressivity/token-saving bet, not a solution to current 12 ms compilation.

[ShadAR](https://arxiv.org/html/2602.17481v1) (2026-02-19 preprint of an ISMAR demo) generates HLSL from speech, but explicitly reports **30–45 seconds** until application and notes imperfect perceptual accuracy. Its “real-time” description concerns interactive rendering, not the required source-to-visual deadline. [ShaderBench](https://github.com/harsh2204/shaderbench) is a useful shader-quality demo/evaluation collection, not a controlled explanatory-readiness benchmark. [WGSL's specification](https://www.w3.org/TR/WGSL/) distinguishes shader creation, pipeline creation and dynamic errors; successful compilation alone is insufficient.

**Smallest decisive experiment:** three public tasks—wave interference, a vector field and an implicit surface—using equivalent native geometry and expression kernels. Compare generated tokens, compile/pipeline latency, frame cost, object correspondence and causal correctness. Reject full generated renderer boilerplate; it expands failure surface without addressing the observed bottleneck.

## Speculation: useful overlap, limited benefit here

[PASTE](https://arxiv.org/abs/2603.18897) (revised 2026-06-16) predicts tool invocations and isolates speculative results until confirmed; its reported gains concern tool-heavy agent workloads. Borrow isolation and dependency validation, not its speedup numbers. Overlapping 12 ms compilation with eight seconds of generation cannot save seconds. More useful speculative work is preparing reusable resources, glyphs and geometries already justified by past evidence while the lecture continues. Predictions of future content must not become visible facts or reset evidence deadlines.

Distinguish **application speculation** (prepare/validate scene chunks early) from **speculative decoding** (draft tokens verified inside the model-serving engine). The latter requires a controllable inference backend; it is not something the existing client can enable by adding a second prompt. Racing two remote authors multiplies cost and still requires a reliable quality selector. A small-model draft followed by a serial large-model correction recreates the current deadline problem.

## Immediate decision

Start with bets 1 and 3 on the present runtime, with the provider experiment prepared as an independent comparison. Use existing subscription calls only within existing authorization; the external API benchmark remains unexecuted. Keep causal planning inside the single source-grounded request, and use a compact generic representation that a trained student could eventually learn. Require blind full-motion review and quality-qualified deadline success before calling any option an improvement. The evidence supports these experiments; it does not yet support a ten-second acceptance claim.
