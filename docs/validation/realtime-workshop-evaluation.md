# Real-time lecture scene evaluation protocol

Status: evaluation planning, not acceptance or a claim of achieved performance.

## User requirement and scope

Create and manipulate explanatory scenes from lecture input within ten seconds,
across arbitrary subjects, with quality very similar to or better than the
baseline, assessed by fresh critical independent reviewers. The evaluation must
preserve the full requested explanation, scientific meaning, stateful manipulation,
and visual quality. A restricted subject catalog, generic diagram, first pixel,
or shorter explanation does not satisfy that requirement.

No finite suite proves universal success on arbitrary subjects. Report the scope
actually tested, unresolved cases, and uncertainty. A successful pilot authorizes
broader evaluation; it does not redefine the requested scope or establish completion.

## Baselines and frozen comparison conditions

Use two complementary references:

1. The user's previously approved Euler visual style, using the approved reference
   images and available motion reference from the explanation-style skill. This
   anchors construction, continuity, annotation and motion quality across topics.
2. A task-matched baseline generated by the established production pipeline from
   the same lecture input, teaching obligations and current carried state. Preserve
   its actual output, including defects and failures; do not select a weak control.

The historical scene-speed fixtures and saved outputs are regression anchors, not
the sole baseline or a substitute for new task-matched comparisons. Freeze input
bytes/hashes, required coverage, source intervals, model configuration, prompt
version, runtime/renderer revision, asset inventory and delivery viewport. Both
arms receive equivalent task information and resources. If an optimization changes
the architecture or model, record it as the experimental factor rather than hiding
it among uncontrolled differences. Counterbalance run order and retain every trial.

No manual refinement of one arm is permitted. Repairs performed by its intended
pipeline remain part of that arm and its elapsed time. Freeze comparison artifacts
before review; do not overwrite failed trials with successful retries.

## Timing contract

Use a shared trace/request ID and monotonically increasing revision ID. Store UTC
timestamps for provenance and monotonic elapsed measurements within each process.
Measure the end-to-end interval on a single client clock where possible; cross-host
timestamps require measured clock alignment and an uncertainty bound.

| Timestamp | Event |
| --- | --- |
| `t_object` | The relevant board/slide object first appears in the source stream. |
| `t_sample` | The capture system samples that object. |
| `t0` | The last input required to determine the requested scene or edit becomes available to the client, e.g. committed text, captured required image, or the end of the necessary spoken clause. |
| `t1` | Server receives the required input. |
| `t2` | Transcription and interpretation produce the actionable scene request. |
| `t3` | Generation returns the proposed scene or edit. |
| `t4` | Assets, compilation and required validation/publication gates complete. |
| `t5` | Client receives and prepares the approved revision. |
| `t6` | The production renderer presents the complete usable revision with its required controls responding. |
| `t7` | A requested animated manipulation reaches its intended endpoint, when applicable. |

The user expanded the deadline from five to ten seconds. Primary readiness latency
is `t6 - t0 <= 10,000 ms`; retain the five-second success rate as a diagnostic,
not an acceptance requirement. Determine `t0` from the frozen
source/command requirements, never retrospectively to make a late result pass.
Speech transcription, transport, queueing, asset fetch/preparation, compilation,
required review, automatic repair and retries after `t0` all count. Do not delay
input commitment artificially or move expensive work outside the clock without
disclosing that work and proving it did not use future input.

Report capture cadence delay `t_sample - t_object` and object-to-visible latency
`t6 - t_object` separately. A ten-second post-input result does not imply a
ten-second response to an object when capture occurs every ten seconds. Also
record the start of each spoken/input interval so buffering and endpoint detection
cannot disappear from the report.

First meaningful pixel is diagnostic only. A title, placeholder, stale revision,
generic construction, partially streamed scene or missing required asset does not
qualify as `t6`. Prove readiness using the exact published artifact, renderer
presentation evidence, and successful required interactions. A render call or
animation-frame callback alone is not proof of actual visible presentation.

For intentionally paced explanatory motion, report both readiness and
`t7 - t0`; do not force a useful longer demonstration to finish in ten seconds
or count an inert scene as a completed manipulation. Define the distinction per
task before running it. Verify that the complete requested motion was available at
readiness and subsequently plays correctly without further generation.

A deadline miss is a miss even if a later result succeeds. Report eventual latency
and outcome as well. Include errors, cancellations caused by backlog, rejected
results, stale updates and incorrect results in the outcome ledger. A timely wrong
scene fails the combined requirement.

## Initial falsification pilot

Use a small, deliberately varied set to expose architectural failures quickly:

- Several source-grounded statics/friction operations from the supplied German
  lecture, including creating a construction, manipulating it, and correcting an
  assumption while retaining object identity.
- Known RNA-pairing and area-derivative regression tasks, to detect loss of visible
  mechanism against historical evidence.
- Fresh lecture-derived tasks from other domains, selected before generation:
  examples include signed-field cancellation, enzyme inhibition, an economic
  shift versus movement along a curve, and historical chronology with uncertainty.
  These are selection suggestions, not a permitted-subject list.

Each selected scenario must exercise creation and subsequent stateful changes.
Include unseen values and paraphrases, geometry not available as a prepared scene,
and supported spatial construction with actual navigation where the topic needs it.
Repeat both arms and counterbalance order. Include cold asset/scene paths and the
intended warm operating mode, documenting generic preloading and cache state.
Do not precompute the scenario-specific answer.

Fix the pilot's tasks and repetitions before observing results. Report all outcomes
and use failures to decide what must change. A small successful set is only a
screening result, never acceptance of arbitrary-subject performance.

## Coverage and quality gates

Create a requirement matrix before generation: required entities, relationships,
inference steps, notation, qualifications, reveal order, controls, carried state,
and semantic invariants. Link each obligation to source evidence and the expected
visible behavior. Distinguish explicit source/user requirements from evaluator
preferences. Missing required content is a failure; reducing coverage cannot buy
speed or visual simplicity.

Review four independent gates, each `ready`, `revise`, or `unverified`:

| Gate | Required evidence |
| --- | --- |
| Reasoning and coverage | Source-faithful meaning, all obligations present, correct mechanism/invariants, and a visible operation earning the inference. |
| Visual readability | Native-size legible labels and geometry, no consequential clipping or sustained overlap, understandable focus and reading holds. |
| Reference style | Topic-appropriate construction owns the frame; meaningful object identities persist; annotations/algebra connect locally; color roles and purposeful motion support reasoning. |
| Technical delivery | Actual complete playback, usable requested controls/navigation, correct state handoff, no runtime failure or stale revision, and audio synchronization when applicable. |

Do not average a failed or unverified gate into a passing score. Request a pairwise
quality judgment as well: materially worse, slightly worse, equivalent, slightly
better or materially better, with timestamps, concrete evidence and confidence.
"Very similar" permits appropriate topic-specific visual choices and minor
imperfections; it does not permit a substantive new defect or omitted obligation.
Pre-existing baseline defects do not excuse new candidate defects. An inadequate
baseline also does not lower the absolute coverage/correctness gate.

## Native evidence and blind review

Use the actual animlib renderer, not approximated diagrams or code screenshots.
`shared/animlib/tools/render-frames.mjs` accepts source, carried frame, models,
sample times and output directory; it emits native WebGPU images at 1280x720 and
960x720 with a frame manifest. It accepts up to 16 times per invocation. Capture
start/end states, semantic milestones and transition interiors, plus dense samples
around suspected problems. Select comparable semantic moments for both arms;
uniform sparse samples and endpoints alone can miss failures.

`shared/animlib/tools/render-video.mjs` can produce native silent motion proofs.
Separately record production-player playback, input interactions and audio evidence
when claiming those behaviors. Offline rendering establishes artifact appearance,
not end-to-end latency or working live interaction.

Package each pair under opaque IDs with randomized `A`/`B` assignments. Supply the
same task requirements, references, timestamp maps, native frames and motion
evidence. Remove variant/model names, latency results, implementation commentary,
identifying source comments and revealing parent paths from reviewer-facing files.
Keep mapping keys outside the blind package. Preserve hashes linking blinded files
to their original outputs. Give sanitized source only when needed to substantiate
correctness; visual conclusions require rendered evidence.

Fresh critical independent reviewers must have no inherited implementation
conversation, author self-score, desired winner or assignment key. Coverage review
and visual review are mandatory. Reviewers identify exactly which frames, motion
intervals and interactions they inspected, distinguish missing evidence from
demonstrated defects, and qualify unsampled behavior. Include an occasional swapped
duplicate pair to detect order bias. Freeze verdicts before unblinding. A repaired
artifact needs new native evidence and renewed affected checks; an old approval
does not transfer to changed source.

## Broader evaluation and completion evidence

After development on the pilot, evaluate fresh held-out online lecture material
across unrelated subject families, representation types, languages/input styles,
symbolic and spatial reasoning, procedural and qualitative explanations, creation,
stateful manipulation and correction. Include continuous sessions, real input
cadence and bursts, long accumulated state, asset/cache variation, required
interaction poses, and ambiguity or uncertainty that must be represented honestly.
Use unseen tasks/values rather than only renamed versions of known constructions.

Predeclare a justified sample and repeat plan based on observed variability and the
claims being tested. No arbitrary number of operations is a magic completion gate.
Increasing repetitions of the same easy task does not establish subject breadth.
Holdouts used to tune a candidate become development data; obtain fresh holdouts
for the final assessment. Preserve the full user's scope when reporting failures.

Report latency median, tail percentiles, maximum, deadline success/failure counts,
and uncertainty intervals, broken down by subject, operation and cold/warm state.
Report combined timely-and-correct-and-quality-accepted success, not speed only
among successful outputs. Include evaluator agreement and every unresolved quality
finding. Any statistical inference must state its independence and sampling
assumptions; a confidence interval does not prove universal arbitrary-subject
behavior or a deterministic latency guarantee.

Completion evidence must include task-matched baseline comparisons, approved-style
comparison, full required coverage, fresh independent blind judgments, real visible
readiness measurements, and live manipulation/playback proof for the delivered
implementation. Clearly distinguish demonstrated results, supported generalization
and remaining limitations. Do not mark the user requirement achieved merely
because a pilot passes, a renderer microbenchmark is fast, or generated code compiles.

## Existing evidence and its limits

- `docs/scene-speed-results.md` and `data/scene-speed/`: useful frozen fixtures,
  paired scene sources, timing and failure records. Their generation timings
  exclude frozen planning and speech synthesis; they are not lecture-to-visible
  end-to-end measurements.
- `docs/scene-speed-visual-review.md`: actual sampled visual comparison, including
  lost mechanism, readability and renderer failures; its limits are explicit.
- `data/review-efficiency-semantic-20261015/result.json`: deterministic host/sampling
  benchmark with `nativeRendered: false` and scripted reviewers. Its elapsed time
  does not measure real-model latency or prove visual quality.
- `docs/demos/quality-comparison/test-3-blind-review.md`: an existing blind review
  example that separates sampled readability from unverified full delivery.
- `docs/instruction-architecture.md` and `backend/prompts/scene-verify.md`: current
  instruction ownership and visual verification requirements. Historical experiment
  reports do not override current production policy.

This document creates no new acceptance evidence. New candidate quality must be
judged from its rendered output and behavior under the protocol above.
